## item 75

**Plain language —** When the desk bought Oracle on 2 September, the chart analyst set a profit target of $159.52 — a price Oracle had already failed at twice. Every seat saw that number: the portfolio manager used it to justify buying, the risk manager saw it, and the position reviewer was shown it every session with the words "soft — you manage exit". But nothing ever used it to sell. The reviewer is told it manages the exit, while its sell rules refuse "taking profit" as a reason, and the "past target" warning only appears at 150% of the way there. Oracle traded above the target on 4 and 8 September. Selling at target would have made about 9%; the desk would have ended slightly below its purchase price.
**Example —** A target is written down before the trade opens, used to say the trade is worth taking, then ignored for the rest of the trade's life.
**The decision —** You asked for each position's target to be shown on the Mission Control chart, and for using it to be debated rather than dropped. Paper-trading "sell at target" for a week was argued against: too few trades to tell luck from skill, one market mood, and it would muddy the restart with a new manager model at the same time.
**Recommendation —** Show the target on the chart. Then track, without placing orders, what four exit rules would have done on every trade — sell all at target; sell half at target and trail the rest; hitting target tightens the trailing stop instead of selling; and today's desk — with the rules fixed before anyone looks and no tuning afterwards. Nothing is built on one trade.

**Rewritten 2026-10-01 — the two derivations of a trim fraction that FAILED, written down so neither is retried blind.**

**Attempt 1 — read the fraction off the position's own risk (trim back to the original risk budget).** Sell the share of the position that restores the risk the trade was opened with, now that the stop has ratcheted. The fraction is `1 - d0/d1`, where `d0` is the entry stop distance and `d1` the current one. The desk's ratchets move the stop to multiples of `d0` that the owner ratified (+1R, +2R), so `d0` cancels and the fraction is the SAME number for every name, every sector, every volatility. It looks per-name and is algebraically a global constant. Rejected: a global risk constant is a defect on this desk, not a value to ratify.

**Attempt 2 — read the fraction off how far the position has weakened.** Scale the trim by the ATR distance already travelled below the last mark, as a share of the full alignment-exit tolerance. Rejected for two independent reasons: the denominator is the alignment-exit tolerance, which that module's own docstring and its ledger entry declare to be owner appetite and NOT sourced, so the fraction inherits an unsourced denominator and is an appetite dial in disguise; and no record exists of any position ever sitting in that intermediate band, so there is nothing to read the shape off even if the denominator were sound.

**What the live code actually does, checked 2026-10-01 (claims in the original filing had rotted).** The target reaches no broker — still true. TARGET_BREACH remains a barred SELL reason. The alignment exit (`src/risk/alignment_exit.py`) sells a WHOLE position and contains no partial path, so the trim case is genuinely untouched by it.

**BUILT 2026-10-01 — the recording the item turns on: `alignment_exit_readings`.** One row per open position per run, written whether or not the exit fires. Before this, only a FIRING alignment exit left any trace, so the population the whole question is about — positions that weakened and then recovered — was invisible and the question "do positions pass through a DURABLE intermediate band of weakening before the trend ends, or do they fall straight through?" could not be asked at all.

**What is stored, and what deliberately is not.** The row carries the symbol, the run, the session date, the side, the verdict status and code, the raw give-back distance in that name's own ATR (`breach_atrs`), the tolerance the verdict was judged against (`band_atrs`), how many sessions the mark has been lost, the last mark's price and source, how many marks the chart presented, and which average the thesis named. NO band edge, NO threshold, NO horizon and NO classification is stored: "weakening", "durable" and "recovered" each need a cutoff nobody can source today, so only raw distances are kept and a later reader states its own cutoff. Unknown is NULL — an UNPARSEABLE read still writes a row with a NULL distance, because "the chart could not be read" and "the chart was intact" are different facts and neither is a zero.

**It is the reading the exit ALREADY computes, not a second one.** The write takes the memoised `AlignmentExitCheck` the scan itself acts on, so the record cannot disagree with the decision. Nothing about when the exit fires, or what it does, changed, and no call order changed. A recording failure is swallowed and never blocks a sale.

**THE RECORDING BUYS NO DATA TO FILL ITSELF, and an earlier draft of it did.** That draft moved the chart read ahead of the priority check so every position would be read, and called the change behaviour-neutral. It was not. A chart read is `pipeline._alignment_exit_for_holding` -> `market.get_ohlcv` -> a live `yfinance` download, uncached, one HTTP round trip per symbol per call; `compute_indicators` and `find_structural_levels` then run on those bars in-process. No model and no paid provider is reached — `yfinance` is free and the Alpaca fallback is inside the existing broker subscription — so the cost is network calls and wall-clock, not dollars. The worst case on an eleven-position book was eleven extra downloads per run, one for each position the scan would have skipped, and the memo would NOT have absorbed them: `_alignment_exit_cached` is called from only two places, the scan and the downstream confirmer, and the confirmer only runs on a sale whose own reason claims the alignment exit, so a name the review wanted sold for an earnings miss would have been downloaded purely to fill this table. The build therefore records what the scan already computed and writes the rest as an explicit NOT EVALUATED row — `not_evaluated_reason` set, every reading column NULL. A later reader needs those rows to know its own denominator and must not read a NULL reading as an intact chart.

## ANSWER to the fourth criterion, 2026-10-04 — positions DO sit in an intermediate state, but weakening is NOT distinguishable from noise. The whole-position alignment exit is the answer and the partial trim is unfounded.

**The desk's own record is still empty, so it could not be the source.** `alignment_exit_readings` has no rows and the table does not exist in `data/quant_agent.db` or in the 2026-09-30 backup — no session has run since the build, so the migration has never executed [measured 2026-10-04]. Waiting for it was not the only route: the question is about market behaviour, and recorded market INPUTS answer it, which doctrine permits where the desk's own outputs do not.

**Sample and method.** The same cache the alignment study used: 19 symbols, 9,519 daily bars, 2024-09-30..2026-09-29 [measured]. The same synthetic-position chain as `measure_alignment_v2.py` — enter at the first measurable bar, hold until the shipped three-leg exit fires, re-enter the next bar; 256 positions, 237 of which ended in a fire [measured]. Harness: `/home/ubuntu/qamc-measurements/measure_weakening_band.py` (outside the repo).

**NO NUMBER WAS CHOSEN, and that is the point.** The alignment exit is three legs that must agree — structure broken by `BREAK_CONFIRMATION_ATR_MULTIPLE`, close under the chandelier at `CHANDELIER_ATR_MULTIPLE`, and the rising-MA veto clear. "Weakening" is therefore read off the COUNT of legs agreeing, 0 to 3. That is a discrete state the desk already computes, not a band width, a threshold or a horizon anyone picked. The failure of attempt 2 was that its denominator was an unsourced appetite dial; a leg count has no denominator to source. Every constant used is pre-existing and owner-ratified.

**The band is real and it is long.** Positions spend 36.3% of all their closes with exactly two of the three legs agreeing — 3,044 of 8,379 measured closes, more time than they spend in any other state [measured]. There are 634 contiguous episodes of it, median length 3 sessions, and every single one of the 237 exits was preceded by at least one such session; 76% had two or more, 59% three or more [measured]. So the literal question "is there a durable intermediate band" is YES.

**But entering it predicts nothing, which is the finding that kills the trim.** Of the 634 episodes, 237 (37.4%) escalated to a real exit and 397 (62.6%) decayed back below two legs with no exit at all [measured]. The two groups are the same length — median 3 sessions each — so holding on for more evidence does not separate them [measured]. Forward return 14 sessions on is +1.42% median from a two-leg close against +1.46% from a three-leg close and +0.74% from a one-leg close [measured]: the "weakening" state is not a losing state, is no worse than the state the desk actually exits on, and is BETTER than the state it treats as healthy. A trim keyed on this band would sell into 634 episodes to catch 237 trend ends — 2.7 trims for every real one — at a point where the measured forward return is positive.

**What this rules out, and what it does not.** It rules out keying a partial trim off the alignment exit's own legs, which was the only threshold-free source left after the two 2026-10-01 derivations failed. It does not prove no weakening signal exists anywhere in markets; it proves that the signal THIS desk computes does not carry one, and that any trim built on it would be selling a state measured to be as good as the one it holds through. The trim question is therefore closed as unfounded rather than deferred, and the whole-position alignment exit stands as the whole answer.

**Honest limits.** Synthetic long positions on a chained re-entry model, not the desk's real holdings — deliberately, since fitting to the desk's record is barred. Daily bars only. One two-year window containing one broad market regime; a different regime could move the forward-return numbers, though it would have to reverse the sign of the 2-leg/1-leg gap to change the conclusion. The 2-of-3 state mixes three different pairs of legs and they were not separated; a pair-specific signal is the one stone left unturned, and nothing above claims otherwise.

## CORRECTION + FIX, 2026-10-04 — the table DOES exist in production, and both swallowed failures are now loud

**The claim above that the table does not exist is WRONG and is corrected here.** `alignment_exit_readings` is present in `sqlite_master` in the live database [measured 2026-10-04, read-only]. So the migration HAS run and sessions HAVE executed the scan: the table is empty because the scan wrote nothing, not because nothing ever ran.

**Why an empty table carried no trace of the failure.** Two broad catch-alls sit on this path — the per-position one inside `_alignment_exit_scan` and the one wrapping the write in `_record_alignment_reading`. Both downgraded any failure to a single `logger.warning` line, and those lines are not stored in the database. A session where the scan broke on every position and a session where the scan never ran produced byte-identical data: nothing.

**Which of the two swallowed it is still UNCONFIRMED, and is now made observable rather than guessed.** A position the scan fails on is written as an explicit not-evaluated row naming the exception type and message — the same row shape the already-proposed-exit skip branch writes, so no chart read is bought to fill it. A write the database itself refuses is logged with `logger.exception`, so the traceback names the layer that refused it. The next session therefore distinguishes the two by itself: rows present with failure reasons means the evaluation broke; still-empty with an ERROR traceback means the write broke.

Covered by `tests/test_alignment_reading_failures_are_loud.py` (4 tests), including both catch-alls firing at once.
