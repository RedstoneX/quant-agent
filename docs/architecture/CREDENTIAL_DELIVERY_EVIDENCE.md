# Credential delivery — empirical HTTP-stack compatibility evidence

Status: reference evidence only, not an architecture document. See `docs/STATE.md` / `docs/WORK.md` for the accepted credential architecture (upstream OneCLI) and for why the custom proxy from `2207b0b74287101ea65ce79782081e51a27420ba` is rejected and must not be revived.

## What this preserves

Regardless of which `HTTPS_PROXY`-based credential-injection mechanism ends up in front of QAMC (upstream OneCLI's gateway, in the accepted direction), the following facts about QAMC's actual dependency code were established empirically — with a disposable local test harness (self-signed CA, a fake HTTPS provider mimicking each real service's exact header/query-param pattern) against real QAMC code paths, not assumptions — and remain true:

- **OpenRouter / `httpx`** (the `openai` SDK's transport, used by all 9 agents): honors `HTTPS_PROXY` by default; CA trust via `SSL_CERT_FILE`.
- **Alpaca / `requests`** (`alpaca-py`'s actual `Session()`, confirmed from source): honors `HTTPS_PROXY` by default, but **does not honor `SSL_CERT_FILE`** — only `REQUESTS_CA_BUNDLE` establishes trust for this library. Two-header credential injection (`APCA-API-KEY-ID` + `APCA-API-SECRET-KEY`) is required — a single bearer token is not sufficient.
- **FRED / `urllib`** (`fredapi`'s actual transport, confirmed from source — not `requests`): honors both `HTTPS_PROXY` and lowercase `https_proxy`; CA trust via `SSL_CERT_FILE` (OpenSSL-level). Credential injection is via query parameter (`?api_key=`), not a header.

**Conclusion that stays true regardless of mechanism:** QAMC's `.env` (or whatever env OneCLI's gateway is invoked under) will need to export **both** `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` (not just one) for all three of QAMC's HTTP stacks to trust the proxy, and the credential-injection mechanism must support header injection (2 distinct header names for Alpaca) and query-param injection (FRED), not header injection alone. This does not need to be re-derived when OneCLI is provisioned — it should be used directly to write the commissioning verification checks.

## OneCLI's own install requirements (verified against upstream, 2026-08-11)

`github.com/onecli/onecli`'s documented Quick Start (`curl -fsSL https://onecli.sh/install | sh`) fetches an install script that checks for `docker`, a running Docker daemon, and `docker compose`, exiting immediately if any are missing, and deploys PostgreSQL via Docker Compose (not an embedded database) for that path. The `dev` account has neither Docker nor passwordless `sudo`, which is why this is a privileged `ubuntu` action rather than something `dev` can complete alone.

## OpenRouter integration: confirmed live, 2026-08-12, zero code changes needed

Once `ubuntu` provisioned OneCLI (Docker install + `docker compose up`, see `ops/onecli/README.md`) and a Custom Secret ("OpenRouter - QAMC", host `openrouter.ai`) was created and assigned to the Default Agent through OneCLI's own dashboard (operator action — `dev` never saw the real key), the exact integration mechanism was determined by querying the running instance's own `GET /api/container-config` API (documented at `onecli.sh/docs/api-reference/agent-setup/get-container-configuration.md`), not assumed from general product marketing. It returns, per-agent: proxy environment variables (`HTTPS_PROXY`/`https_proxy` in the form `http://x:<agent-token>@<host>:10255`), the gateway's CA certificate (PEM, returned inline), and placeholder credential stubs for OneCLI's own built-in providers (Anthropic/OpenAI only — confirming the operator's finding that built-in keys don't cover OpenRouter; a Custom Secret has no such stub because it's matched purely by destination host at the gateway, not by a known env-var name).

One correction needed versus that endpoint's raw output: it returns `host.docker.internal` for the proxy host, which resolves inside a Docker container but **not** for QAMC's trading engine / Mission Control, which run as bare processes under the `qamc` account — confirmed the gateway is also bound to `127.0.0.1:10255` directly on the host (`ss -tln`), so `host.docker.internal` must be substituted with `127.0.0.1` for QAMC's actual `.env`.

**Mechanism proof (not theoretical):** an obviously-fake `Authorization: Bearer sk-or-placeholder-not-a-real-key` sent to `https://openrouter.ai/api/v1/auth/key` (an endpoint that validates the key) returned `401` when sent directly, and `200` when routed through the OneCLI gateway with CA trust — the only variable changed was the routing path. This proves the gateway is substituting the real credential server-side; the placeholder never became valid on its own. Both requests discarded response bodies (`-o /dev/null`) — the real key's value, and any account/usage metadata `/auth/key` might return, was never read or logged by this verification.

**Why zero code changes are needed:** `src/agents/base.py`'s OpenRouter branch already constructs its `OpenAI(...)` client (line ~553) without a custom `http_client`, so the SDK's underlying `httpx` client uses its own default environment-driven proxy/CA trust — exactly the `HTTPS_PROXY`/`SSL_CERT_FILE` behavior already established above for the `httpx` transport. `_OPENROUTER_BASE_URL` stays `https://openrouter.ai/api/v1` unchanged (QAMC keeps calling the real host; the gateway intercepts transparently), and `config/settings.yaml`'s `<agent>_provider`/`<agent>_model` values are unrelated to credential delivery and stay unchanged. The only required change is runtime configuration: `HTTPS_PROXY` and `SSL_CERT_FILE` added to `/home/qamc/quant-agent/.env` (see the pointer comment added to `.env.example`), which `dev` cannot apply directly since `dev` cannot write into `/home/qamc`.
