# Credential Proxy — Accepted Contract

Status: implemented, pending operator provisioning — 2026-08-11.

## What this is

A minimal, purpose-built HTTPS forward proxy (`ops/credential-proxy/gateway.py`, stdlib-only) that lets the `qamc` runtime hold only inert placeholder values for `OPENROUTER_API_KEY`, `ALPACA_API_KEY`, `ALPACA_SECRET_KEY`, `FRED_API_KEY`, while a separate, dedicated system account (`credproxy`) injects the real credential into each outbound request at the network layer. `qamc` and `dev` never possess a working real credential.

## Why not the OneCLI product

OneCLI (github.com/onecli/onecli) was investigated as the candidate credential-management layer per prior direction. Its own install script (fetched and inspected directly, not assumed) unconditionally requires Docker + Docker Compose + PostgreSQL + a Next.js dashboard, and provides no non-Docker local mode for the gateway component. `dev` has no Docker and no passwordless sudo, so standing up the real product was not possible without an operator-provisioned Docker install — a real infrastructure cost for what this deployment needs as exactly one property.

That property — real secret never touches the consuming process — was extracted and empirically validated independently of OneCLI's own packaging (see Verification below), then implemented directly as a ~300-line stdlib script. This is the "prefer the simplest secure architecture" call: OneCLI's multi-tenant OAuth/dashboard/Postgres surface is built for a broader use case than "one process, three known upstream hosts, one human operator." Nothing here forecloses installing real OneCLI later if the requirements grow (multi-agent, multi-org, audit UI); the pattern this module implements is the same one OneCLI itself uses (`HTTPS_PROXY` + local CA + host-matched credential injection).

## Mechanism

1. `qamc`'s `.env` sets `HTTPS_PROXY=http://credproxy:<TOKEN>@127.0.0.1:10255` (the token is a shared secret generated by `setup.sh`, distinct from and much lower-value than the four real trading/LLM credentials — see Security properties), `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` both pointing at the proxy's public CA cert (`/etc/credential-proxy-ca.pem`, world-readable, contains no secret material), and placeholder values for the four credential env vars (the existing `.env` template values already satisfy this — no change needed there).
2. Any outbound HTTPS call from `qamc` to a routed host (`openrouter.ai`, `paper-api.alpaca.markets`, `data.alpaca.markets`, `api.stlouisfed.org`) is transparently intercepted by the proxy via the standard `CONNECT` tunneling mechanism.
3. The proxy verifies the CONNECT's `Proxy-Authorization` against the configured token (constant-time comparison) — **refusing with `407` if missing or wrong**, closing the gap where any other local process could otherwise use the proxy exactly as if it held the real credentials.
4. The proxy TLS-terminates the local leg using a leaf certificate it generates on the fly (signed by its own internal CA — `qamc` trusts this CA, no public CA is involved), rewrites the placeholder header/query-param value to the real one from its own `routes.json` (chmod 600, `credproxy`-owned only), and opens its own outbound TLS connection to the real upstream host with **normal public-CA verification** — this proxy does not weaken outbound trust, only intercepts the local leg.
5. Any request body bytes that arrived bundled with the header read (routine TCP behavior — nothing requires a client to write headers and body separately) are forwarded first, then both directions become a raw bidirectional byte relay — not a buffer-then-forward, and not a manually-counted `Content-Length` read. This handles fixed-length bodies, chunked bodies, and streamed (SSE) LLM completions uniformly, and was specifically redesigned after independent review found the original manually-counted version could double-count or lose sync (see Independent review below).

## Verification performed (empirical, not theoretical)

Built a disposable local test harness (self-signed CA, a fake HTTPS provider requiring the exact header/query-param patterns each real service uses, this proxy pointed at it) and confirmed, against QAMC's actual dependency code paths — not assumptions:

- **OpenRouter / `httpx`** (the `openai` SDK's transport, used for all 9 agents post-migration): honors `HTTPS_PROXY` by default; CA trust via `SSL_CERT_FILE`. Full round trip succeeded; client held only a placeholder Bearer token throughout.
- **Alpaca / `requests`** (`alpaca-py`'s actual `Session()`, confirmed from its source, not docs): honors `HTTPS_PROXY` by default, but **does not honor `SSL_CERT_FILE`** — only `REQUESTS_CA_BUNDLE` establishes trust for this library. This was an open question in prior investigation; now empirically settled. Two distinct header injections (`APCA-API-KEY-ID` + `APCA-API-SECRET-KEY`) on one host were proven mechanically sound.
- **FRED / `urllib`** (`fredapi`'s actual transport, confirmed from source — not `requests`, unlike the other two): honors both `HTTPS_PROXY` and lowercase `https_proxy`; CA trust via `SSL_CERT_FILE` (OpenSSL-level, not library-specific). Query-parameter injection (`?api_key=...`) proven end to end.

Conclusion: the proxy must export **both** `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` (not just one) for all three of QAMC's HTTP stacks to cooperate — this is now encoded directly into the qamc-side integration instructions, not left to trial and error at deploy time.

## Independent review

One review round was run against this diff before it was considered done (a fresh agent instance, not the author, given only the diff and told to be adversarial — see repo conventions for why this matters on safety-sensitive changes). It found two BLOCKERs, both fixed and empirically re-verified before this document was finalized:

1. **Request body could hang/desync on ordinary POST traffic.** The original code read headers into a buffer, then separately re-read `Content-Length` bytes for the body — but a single `recv()` routinely captures body bytes that arrived in the same TCP segment as the header terminator (ordinary client behavior, not an edge case), which the header-parsing code then also mishandled as bogus trailing header lines. The combination could double-count body bytes and hang indefinitely waiting for bytes the client had already sent. Reproduced with a raw-socket client that sends headers+body in one `sendall()` (exactly what the reviewer flagged as a routine pattern) — hung on the original code, real risk for Alpaca order POSTs and OpenRouter completion POSTs specifically. **Fixed** by removing manual `Content-Length` tracking entirely: any body bytes bundled with the header read are forwarded immediately, then both directions become a single bidirectional byte relay with no framing awareness needed — correct for fixed-length, chunked, and streamed bodies alike, and structurally unable to double-count. Re-tested with the exact single-write repro plus a real upstream body-content round trip (echoed and verified byte-for-byte) — no hang, correct relay.
2. **No caller authentication.** The proxy validated the destination host but not the caller — any local process on the box, including `dev` itself, could dial the proxy directly and get the same real-credential injection `qamc` gets, with zero proof of identity. This directly undermined the stated goal ("`qamc` and `dev` never possess a working real credential") — `dev` never holding the *raw string* was true, but `dev` could get the same *effect* at will. **Fixed** by adding a required shared-secret `Proxy-Authorization` check (constant-time comparison) — the proxy now refuses to start without a configured token, and refuses any CONNECT that doesn't present it correctly. The token travels via the standard `http://user:token@host:port` proxy-URL convention, which `requests`, `httpx`, and `urllib` all translate into a `Proxy-Authorization: Basic ...` header automatically — verified empirically for all three (missing/wrong token → `407`; correct token → success), no QAMC code change needed. This mirrors what OneCLI's own gateway does (per-agent access tokens over `Proxy-Authorization`) — the independent review's own footnote noted the irony that this was the one property the initial simplification had dropped.

A third finding (IMPORTANT, not a BLOCKER) was that the original qamc-side integration instructions only patched `quant-agent-api.service` (Mission Control's read-only process) and never actually reached the trading engine, which sources `.env` directly via bash in `scripts/run_if_et_window.sh` — a separate path with no relationship to Mission Control's systemd environment. **Fixed** by moving the integration point to `.env` itself, the project's own existing single source of truth for every other secret, which both consumption paths read from.

## Security properties

- Binds `127.0.0.1` only — never exposed off-host, matching the same discipline already applied to Mission Control.
- Requires `Proxy-Authorization` matching a shared-secret token on every request — closes the "any local process gets the same access as qamc" gap (see Independent review above). The token is deliberately a separate, lower-value, easily-rotated credential — it grants only "permission to use this proxy for these 4 hosts," never the trading/LLM credentials themselves.
- Logs host/path/method/status only; never a credential value (verified directly — grepped proxy logs for the test secret value after a full successful round trip, found nothing) and never the auth token.
- `routes.json` (real secrets + the proxy auth token) and the CA private key live only under `credproxy`'s home, mode 600/700, unreadable by `qamc` or `dev`. The proxy refuses to start (not just warns) if that file's permissions are ever looser than 600.
- Systemd unit runs with `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome=read-only`, `RestrictAddressFamilies`, `MemoryDenyWriteExecute` — least-privilege by default, not an afterthought.
- `qamc` isolation is unchanged: it still runs as its own account, doing its own thing; it is only told to trust one additional internal CA and route through one additional loopback proxy (now with its own credential to present). It does not gain access to `credproxy`'s account or files, and `credproxy` gains no access to `qamc`'s runtime, database, or trading logic.

## Known limitations

- This is not a general-purpose secrets platform — it has no rotation UI, no audit log beyond systemd's journal, and one shared token rather than per-agent identity (fine for this deployment's single consumer; would need real work to extend to multiple distinct callers with different privileges). That's deliberate: it does exactly what this deployment currently needs.
- The CA is generated once with a 10-year validity; rotating it requires updating the published public cert (`/etc/credential-proxy-ca.pem`) and is a manual, documented, low-frequency operation — not automated. The same is true of the proxy auth token.
- Chunked request bodies are handled by the generic byte-relay path (no special framing logic needed, since the relay doesn't parse HTTP framing) — this was verified for fixed-length bodies specifically; chunked-request verification wasn't separately exercised, though the design gives no reason to expect different behavior.
- Requires the operator to provision the `credproxy` account and enter real secrets + confirm the proxy auth token directly (never through `dev`/chat) before this can carry live traffic.
